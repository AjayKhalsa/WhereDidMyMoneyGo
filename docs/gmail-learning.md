# Gmail categorization and category review

Gmail reuses `engine/learning.ts`, `engine/parser.ts`, saved `rules` and rule contexts. Scoped user corrections take priority, followed by compatible saved/history rules, reliable food-time rules, merchant vocabulary and the user's small personal-UPI preference. Conflicting applicable categories abstain. Learning never relabels existing ledger records automatically.

Historical evidence includes explicit manual/parsed saves, legacy reviewed `txn_` imports (the pre-receipt user-reviewed archive), and Gmail entries whose saved category differs from the original parser candidate or required an explicit category choice. New machine-generated Gmail/statement entries cannot train from their own predictions. Bootstrap requires three consistent examples for an exact normalized payee, excludes generic activity words and does not replace existing patterns. Evidence records source, normalized merchant, support and example IDs. Conflicting history disables historical suggestions at runtime; scoped explicit corrections remain authoritative. Existing conflicting legacy rules are retained for review, not merged or deleted.

Meal expenses use verified IST boundaries: breakfast 00:00–11:59, lunch 12:00–16:59, snacks 17:00–19:59, dinner 20:00–23:59. An explicit leaf mapping wins. Unknown times produce only the broad food category. Gmail received times never establish actual transaction time. These rules do not assign meal categories to arbitrary merchants.

Outgoing UPI below ₹200 to an identifiable individual can use Transport after saved mappings and known merchants are checked. A usable VPA and person-like name are required; masked identities, business indicators, own-name transfers, credits, refunds, repayments and investment signals are excluded or held for financial-purpose review. The heuristic never invents Auto/Cab specificity.

Migration `0018_gmail_learning_review.sql` adds optional rule evidence and a category-review flag/snapshot on Gmail receipts. Confirmed expense debits with low/unknown category confidence enter the existing ledger as Other and remain visible for category review. Type/account/authentication uncertainty, credits and repayment/transfer/investment signals still require financial review. The app does not claim that every unexplained debit is consumption.

Category approval updates only the category of that same transaction, preserving cash effects, IDs and other manual fields. A full saved-row comparison prevents overwriting later edits; “Keep current entry” dismisses the category request while retaining the logged receipt and ledger entry. An optional payee-specific correction rule is saved atomically with approval. Shared-source matches never inherit an automation category or personal tags. New internal functions remain service-role only; existing RLS and token restrictions are unchanged.

New Gmail observations and historical preview candidates also honor a confident saved rule's merchant alias, using the same saved rule as the entry parser. Aliases never change amount, date, reference, account or direction. Weak/conflicting rules and financial-purpose review cases keep the original payee. A broad brand name does not erase a distinct sub-brand merely because the category rule matched. Already matched canonical ledger rows retain their manually saved merchant unless the user separately requests a historical correction.

Back up all finance/receipt/source tables, rehearse on that backup, seed only reviewed consistent rule proposals, and verify all existing financial rows remain unchanged. Report held-out results with sample size and abstentions, excluding already-trained saved rules from independent metrics. Unknown historical times cannot validate meal predictions. Historical Other-category cleanup and backfills require separate before/after review and approval.
