# Shared import identities

Deploy migrations `0015_shared_transaction_sources.sql` and `0016_atomic_reconciliation.sql` before this release. They add provenance and atomic save functions; they do not insert, delete or recategorize financial transactions.

`transaction_sources` maps multiple Gmail/statement/reconciliation receipts and normalized strong reference identities to one canonical transaction ID. Reference identity includes the resolved account, debit/credit direction, amount and bank reference, so card suffix aliases resolve to the same account and refunds do not collide with purchases. A source includes its date, payload/file hash, matching reason and creation date. A deleted transaction leaves a tombstone receipt rather than being silently recreated.

Gmail and statement saves use the same database matching function. Exact strong references can link to a unique saved event within three posting days without changing its manual description, category, merchant, notes or contexts. Distinct proven references preserve repeated equal payments. A weak account/amount/direction/date collision is a review signal, never proof of duplication. Review supports an explicit existing-entry link or separate-payment confirmation. Conflicting references or changed saved financial details require review. Intentional Gmail dismissals remain untouched.

Statement source keys include the selected account, SHA256 of the original file and parsed row occurrence; stable IDs include the profile namespace. Reference matching also handles overlapping files with different file hashes. Without a strong reference, a changed narration/file remains a conservative review case. An opening-date overlap blocks new financial insertion until the starting history is reconciled. Raw statement files and email bodies are not persisted by this mechanism.

Cloud statement batches and reconciliation bundles commit atomically. Reconciliation compares full before images and contexts, validates ownership/references and checks every affected bank/card closing balance inside the transaction. New ambiguous same-amount reconciliation rows require an explicit `allowSeparate` confirmation in the prepared edit. If a strong reference already has a different canonical ID, regenerate the bundle with that ID; the server never merges entries automatically. Derived stale-checkpoint status is excluded from before-image comparisons while the checkpoint's evidence/fingerprint remain protected.

Gmail, imports, reconciliation and ordinary ledger/context statements use the same per-user advisory lock. Statement-level locks precede row locks to avoid the usual manual-write/import deadlock; trusted jobs also take the lock explicitly. Browser access to source receipts is read-only under user RLS. Browser RPCs derive the user from the authenticated session. Only the existing service role can call the internal/Gmail functions; token-table access is unchanged.

The local/demo fallback has stable per-source IDs and conservative comparisons but no cross-device database lock or persistent many-source receipt table. Use cloud persistence for those guarantees. Bank references absent from legacy rows remain review cases; no speculative historical identity is fabricated.

Regression tests exercise real migrations, cross-source matching, repeated files, differing descriptions, same-day equal payments, refunds, transfers, deleted sources, atomic rollback, stale manual edits, authenticated ownership and RLS. Historical mail scans and new financial-event imports are separate operations requiring their own reviewed dry runs.
