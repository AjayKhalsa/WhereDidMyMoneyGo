# Gmail missing-transaction checks

Settings → Gmail → **Check for missing transactions** compares an explicit period (at most 100 days) with the current ledger. Dates and technical scan counts are collapsed under **Period & scan details**. The last scan's dates are retained; a first scan defaults to the latest 90 days through today in IST. Supported banks and narrowly scoped Groww/KFintech confirmations are covered. Attachments and unsupported formats are not complete account history.

Only possible gaps, unresolved matches and failures appear in the main list. Matched payments, dismissed emails and non-payment reminders stay hidden. A completed scan with no actionable findings says so without implying that an import or approval is pending. All unresolved cases can be reached with Show more; the full audit is an optional download in scan details. Investment allocation values remain distinct from bank debits; no payment is invented from a reminder.

Migration 0019 adds two staging tables with owner-only SELECT RLS; writes are server-only. A shared Gmail connection lease serializes discovery with ordinary sync/disconnect. The run's query is immutable. Message IDs are durably queued before cursor advance, and a replay uses a unique run/message key. Cursor recovery can restart the same query without erasing queued results. Each request lists at most 25 IDs and processes at most 25 observations within a time budget; the UI performs six requests and then offers Continue. Failed messages have at most three processing attempts. Terminal completion requires discovery exhaustion, no queued observations and no failed messages. A completed run is returned unchanged on ordinary retry of its same date range. Settings offers **Check Gmail for missing transactions** to start a new immutable run using current parsers and senders. The explicit `refresh: true` applies only when starting a run; subsequent batches resume it. Previous runs and intentional dismissals remain intact. This also lets new formats be evaluated without changing the requested date range.

The preview never writes ledger transactions, normal Gmail receipts, learned rules, recurring links or balances. Existing ignored receipts remain ignored. Existing logged IDs and unique strong account/reference/direction/amount matches point to the existing canonical transaction. Amount/date collisions, orphan source identities, unknown accounts, credits, financial-purpose uncertainty and category uncertainty remain reviewable. Unsupported messages are reported as skipped. Counts distinguish discovered, processed, matched, proposed, review, ignored, skipped and failed; imported is always zero for a preview. Export contains extracted details and evidence, not raw email bodies or OAuth credentials.

Recurring suggestions reuse existing rules and actual expense transactions. Unique exact merchant/account/amount matches propose a link; different amounts propose review. Income, refunds and ambiguous merchants never count as paid subscriptions. Existing recurring links are retained. Additional known subscription merchants need three distinct monthly charges with 25–35 day gaps to suggest a pattern. Rules, forecasts and paid status remain unchanged until approved links are applied. No payment is synthesized from a renewal reminder or a mandate.

Historical import/link approval is a separate step: back up current data, review the complete exported preview against statements, use the shared source identity and atomic ledger functions, and reject stale/ambiguous matches. A completed scan is neither an approval nor a statement reconciliation. This phase deliberately has no one-click historical apply endpoint. Do not feed staging IDs into the ordinary pending Gmail queue.

Relevant files: `src/lib/gmail/backfill.ts`, `backfill-plan.ts`, `src/app/api/gmail/backfill/route.ts`, `src/components/settings/gmail-backfill.tsx`, `supabase/migrations/0019_gmail_backfill_preview.sql`. Nightly scheduling and automatic recurring-rule creation are separate phases.

The displayed report now overlays current receipt decisions: an email linked to an existing ledger transaction is shown as matched, a later dismissal is honored, and a deleted canonical entry requires review. This updates display only; it does not rewrite the original staging evidence or create transactions. Already matched items are counted for coverage and excluded from the action list.

## Current-ledger matching and obsolete review prompts

Every report refresh checks current source identities, bank references and supported CRED order references alongside account, direction, exact amount and the three-day posting window. A newly represented event disappears from the action list without another scan. Unique canonical IDs and manual labels remain unchanged. Conflicting references, missing/deleted canonical rows, authentication warnings and repeated identical identities remain reviewable. Amount/date/merchant similarity alone cannot prove a match.

The main Gmail review list also hides category prompts already resolved by a changed, valid, specific ledger category. It compares the saved review snapshot with the current entry; notes-only edits, unchanged categories, Other, absent categories and missing snapshots remain actionable. Exact review counts are computed after filtering, using complete paginated reads rather than the first response page. Snapshot payloads are not returned to the browser. This is a read-only display decision; no receipt flag or ledger label is overwritten.

For weaker matches, a single exact-day normalized payee match can be preselected in the existing-entry selector. The user still confirms that link through the existing protected matching endpoint. Multiple same-payee equal-value payments are never arbitrarily assigned.

Validation: focused matching/category-review tests and the full suite cover strong source identity, bank references, provider-reference boundaries, equal payments, missing canonical rows, stale category prompts and manual-field preservation. Chromium's synthetic local harness checks 320/390/1024 layouts, hidden matched entries, collapsed details, empty states, privacy masking and access to more than 15 unresolved cases. No migration or production financial mutation is required for these changes.
